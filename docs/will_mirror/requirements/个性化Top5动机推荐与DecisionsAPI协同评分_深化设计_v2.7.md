## A. 产品决策：把“50+动机”变成用户真正用得上的前五项

**用户目标**：输入现实课题后，AI 可在后台生成约50—70条语义不同的正反候选动机；自动筛选出对**此人、此次课题、当前可比较的行为路线**最值得优先审议的最多5条，显示排序、各维依据、支持/反对路线、未知、可推翻条件及用户反馈入口。默认只占原Case工作台的一组卡片，避免另设导航/问卷；可以展开完整候选池和切换“看重要反方理由”。

**必须分清三个对象**：

- `Motive`：支持、阻碍或促使改道的理由，不是可执行行动；推荐“最值得认真考虑”≠“一定最强的真实心理驱力”，更≠“意志已被识别”。
- `Route`：用户可以采取的实际路径；已有 v1.4 §4B.7 的路径可行性和欲求一致性，**未来可选另做Top5路线**，不得用动机分数假装路径总得分。
- `WantHypothesis`：跨事件的个体欲求候选；**不可**因为某个动机排名第一，就声称它是个体的根本意志、性格或不可改变的价值。

**“最优”的产品定义**：在本次审议与当前证据下，**优先呈现的解释价值/行动决策相关性**，而不是人生意义上的唯一最优解。前五包含合理的反方、保护性提醒、必要信息核实；并非五条只会鼓励行动的句子。如果证据只有2条合格，就只推荐2条并说明；“没有足够依据”是合法结果。

## C. 推荐工作流：LLM理解 → 规则预筛 → Decisions评分 → 约束排序 → LLM解释 → 现实验证

1. **恢复已授权证据**：仅使用当前Case和用户许可复用的历史经历，生成时点快照 `EvidenceSnapshot`：用户自述、行动、真实取舍、已核实事实、待核实信念、各自T0/T1/T2。敏感经历最小化传输；本地模式/不使用远程评分可选。
2. **LLM生成、去重和修订候选**：继承原50—70动机候选，保留 `motiveId / routeId / wantId / evidenceIds / source / polarity / horizon / factStatus`。语义近似但实际作用不同的理由不得误合并；重复描述不要抢占Top5。
3. **安全/事实硬闸门**：健康、法律、他人同意、真实资格、危险路线等不参加普通总分竞争；违反硬约束的支持理由不得成为行动推荐。纯虚构事实、模型臆测、不符合本人的候选降级为`verify_first`或`ineligible`。真实风险可以作为警示动机进入前五，并触发暂停或核实。
4. **两阶段筛选（P0）**：先用确定性规则、事实资格与轻量模型，把全池压缩到有不同观点的约15—25条；必须保留高代价风险、长远理由、现场重要阻力及不同路线反方。可在测试样本上量化召回率；不允许第一阶段仅按语义相似度丢弃少数却决定性的安全/长期候选。候选较少时全部送评；对重要候选可直接送评分。
5. **Decisions API独立维度评分**：按相同评分准则评价每个候选，不把`confidence`当“此人真实欲求概率”。调用失败或拒绝时展示降级排序、`unscored`与待复核，而不是伪造数字。
6. **服务端排序与Top5组合**：只在符合事实及安全约束的可比候选中，用公开规则计算探索性优先级；去重、多样性与关键反方覆盖，防止五项都是重复正方。排序低不代表无价值；显示名次变化和“为什么没入选”。
7. **解释与用户修正**：Responses API可用 Structured Outputs 生成可验证JSON解释，必须引用当时证据ID、反例、适用路线及“何时会改变”；模型只能解释，不得改写后端得分或越过硬闸门。
8. **现场复核与后续校准**：真实条件到来时，核对新事实与动机是否进入意识；在 T1 可重算但保存 T0 榜单；T2根据实际行动/结果/获得后满意、反例调整准则/个人偏好候选，不能反向将事后证据写回T0。

## D. OpenAI Decisions API的实际能力与使用边界（截至2026-10-11）

OpenAI官方公布：Decisions API公开Beta、唯一当前模型 `gpt-6-luna`，路径 `POST /v1/decisions`；请求包含 `model`、共享 `input`（文本或图像消息）与 `questions[]`，三类 `predicate/choice/score`。`score` 针对自定义有序 `levels` 给出0起始等级索引的概率加权平均，响应包括`score / probabilities / confidence`；`choice`选择单个预设值，**不是批量Top5专用算法**。`predicate.probability`是针对输入条件的模型估计，不能等同未来个人行为成功概率。API不替产品核实事实，不自动生成长篇解释或跨样本稳定排序；解释/JSON结构输出使用 Responses API。来源：上述官方链接。

**推荐架构：** 一个或多个 `score` 问题对应“候选motiveId×评价维度”，问句带稳定命名与固定量规。若一批共享上下文过长，拆成批次并控制交叉比较/评分尺度偏移；同一问题多次评分可作一致性评估，不能简单取一次最大数。`choice`可作候选属性分类、冲突立场分组，不推荐反复用`choice`从50条中删除45条作为唯一依据。适配 API 改版必须做契约与回退测试；Beta可用性、费率、SDK版本以正式调用时的文档/账户权限为准。

**示意请求（API格式，非已发送请求；只演示两个维度，实际逐条扩展）**：

```json
{
  "model": "gpt-6-luna",
  "input": "场景与证据：当前目标是评估是否接受一个岗位。用户本人明确认可经济独立的重要性；岗位合约的安全条款仍未知。候选m1：获得稳定收入可支持经济独立。来源：用户当前自述。候选m2：岗位可能存在未确认的安全风险。来源：待核实。",
  "questions": [
    {
      "type": "score", "name": "m1_personal_relevance",
      "instructions": "只用给定证据，评估候选m1与当事人明确认可欲求之间的相关性；不评价它是否必然导致行动；证据不足可给低档并由应用单独标未知。",
      "levels": [
        {"label":"0", "description":"无明确个体关联"},
        {"label":"1", "description":"只有通用或推测关联"},
        {"label":"2", "description":"有一条用户相关线索"},
        {"label":"3", "description":"有直接、明确的本人证据"},
        {"label":"4", "description":"有多项独立、可比的本人取舍或行动证据"}
      ]
    },
    {
      "type": "score", "name": "m2_decision_materiality",
      "instructions": "评估候选m2若得到证实，是否会实质改变当前选择比较或需要优先核实，不将安全疑问自动宣布为事实。",
      "levels": [
        {"label":"0", "description":"与本次选择无关"},
        {"label":"1", "description":"作用很弱"},
        {"label":"2", "description":"可能改变次要比较"},
        {"label":"3", "description":"有理由改变重要取舍"},
```

**后端转换**：每条`score`等级索引0—4先保留原值，若用户显式要求百分制则展示`round(25×score)`的**量规展示尺度**，不能标注“个人真实动机强度85%”或“行动概率85%”。`confidence`与事实证据质量分开存储，模型置信度不自动使事实状态从`reported`升为`verified`。

## E. 五项推荐用什么维度评分？

| 维度 | 参考权重（可调，非科学常数） | 衡量什么 | 常见风险 |
|---|---:|---|---|
| `personal_fit`个人相关性 | 35% | 是否对该人的已认可欲求/真实取舍有依据 | 将一般人的需要误当本人的稳定特征 |
| `evidence_quality`证据质量 | 25% | 是否有当前/历史真实依据、来源与反例，事实状态是否可核实 | API自信不等于证据真实 |
| `decision_materiality`决策区分度 | 25% | 这项理由是否可能让某条路径比较发生实质变化，含安全核实 | 将情绪强烈误当决定性 |
| `context_relevance`当前情境相关性 | 15% | 与当前时点、路线、现实条件及可操作的核实/准备是否相关 | 过分偏向即时理由忽略长远价值 |

**说明**：`priority_raw=0.35P+0.25E+0.25M+0.15C` 仅用于同一个Case、同一版本证据与量规下的审议优先级；四维都以0—4量规归一。所有维度可以是`unknown`；关键`personal_fit`或`evidence_quality`缺失时不强行用0补缺并伪装完整，进入“待核实”池；允许敏感性分析（改权重后Top5是否变化）。用户个人明确的价值权重可经实际取舍校准，不应让模型偷偷替其设定。

**排序后还必须进行集合约束**：优先选择互相独立的五条，至少审查关键反方、重大风险、长远代价与用户认可欲求；不是预设固定正反配额，更不能在真实反方不存在时生成一个。多条高分同义项只保留代表项；同一理由对不同路线可能一正一反，保存 `directionByRoute`。硬风险影响是否推荐路线，不被任意权重抵消。五条均可能不足：显示Top N（N≤5）或“目前无法可靠排序”。

**两套排行榜不得混淆**：

- `Motive Top5`：五条最值得审议的**理由**，可以支持路线A、反对A或建议先核实。
- `Route Top5`（P1可选）：根据现有§4B.7的欲求匹配、难度、事实资格、风险、资源、真实满足预测分别排序的**行动路线**；它不等同于按动机总分相加得出的行为必然性。若只有两条可行路线，最多显示两条。

## F. 手机交互规范：Top5默认卡，而不是50道选择题

**原Case工作台**新增一张“本次最值得考虑的5条理由”卡：标题下显示适用路线、证据时点、更新时间；每个条目 `序号—理由概述—本次审议优先级/待核实—支持/反对的路径—证据简述—查看为什么—反证/条件`。排序可显示“本次优先审议第1位”，而非“你内心最强意欲第1位”。

用户操作：`认可这条理由`、`不符合我`、`核实事实`、`为什么它排前面`、`显示重要反方`、`看全部候选`、`修改权重`（高级选项）、`不使用远程评分`。用户“不符合”应直接导致该个人关联降级，除非涉及独立真实安全约束；必须显示为什么仍保留风险提示。点击通知跳转原Case的该榜单快照，不额外新增模块。

**示例（虚构，非真实评分输出）**：若某人比较接受一份岗位与先核实条件，前五可能包含“稳定收入的重要性”“工作安全条款待核实”“长期技能成长”“实际通勤成本”“现场逃避不适”；其相对次序必须由本人证据而非这套模板决定。比如安全条款风险若严重，应先核实，不因“收入理由分高”直接推荐签约。

**无数据/离线**：显示“暂无可靠Top5，先核实最影响选择的一件事”，保留现有6—8条代表性动机阅读模式/本地缓存；无网络不假装刚得到 Decisions 最新评分。

## H. 鲁棒性、隐私、正确性与评价

- **公平多面性**：不能只按词面相似挑五条；过去没做过不等于将来无可能，见§4B.19。
- **证据撤回**：用户撤回某行动、欲求或共享授权后，所有依赖该证据的Top5标过期；UI可查看历史，但新报告必须重算。遵守删除/隐私范围。
- **偏差敏感性**：检查不同措辞、顺序、提示长度、证据真假、同义重复、冲突理由、模型版本是否导致不稳定排序。独立维分互相高度相关时需重新设计量规，不能把重复信息计算四遍。
- **真实效果**：先评估“事实引用正确率、重要反方覆盖、误报硬风险率、Top5人类评审接受度、缺失项审慎处理、排序稳定性和可解释性”；随后才探索是否改善真实决策质量，不能用用户被触动或点击次数冒充行为效果。
- **高风险**：健康、安全、工作资格、法律、关系等事实不足时允许“先核实”和“暂不排名”，不以API高分绕过风险闸门；尊重用户自主。保护性暂停可能优于任何行动。
- **透明调用**：告诉用户是“AI辅助的审议优先级推荐”，而非“官方 OpenAI 权威心理分”；说明数据用途、可关闭远程调用、允许删除和撤回。

## J. P0/P1实施顺序及验收方案

**P0**：完成Top5动机候选排序的事实/安全预筛、Decisions API `score`适配器、可解释权重、多样性与反方保留、原Case卡片、反馈重算/快照、联网失败降级、T293—T326测试；优先采用不需要主观心理概率的评分量规。线上 API可用性和真实延迟/费用要由开发阶段压测确认，不能以官方文档代替实测。

**P1**：支持经用户确认的个性化权重、独立的`Route Top5`、跨Case长期校准和更丰富可视化；P2才考虑随机对照的决策辅助效果评估，必须自愿、低风险、保护隐私。

## K. 结论：排序的是“当次决策证据优先级”，不是性格本质

新增的Top5机制把原本覆盖广泛的动机图收敛为小屏可理解、有证据、可反驳、兼顾正反观点的决策工作台。其价值来自复用已有的欲求和现实行为证据，降低认知负担，而非将个人的全部意欲化约成5个数字。Decisions API负责遵循固定量规给出结构化评分，最终约束、去重、组合、解释以及真实性仍由应用系统承担。
