## 修复的问题

| 原有触发条件 | 后果 | 修复 |
| --- | --- | --- |
| 较轻人声进入 warm 候选，但后续仍要求高 RMS；播报后还额外要求强人声 | 用户说话不被录入，尤其是紧接 AI 回复的第一句 | 统一开口/续句门槛，固定 20ms 帧，240ms 滚动窗口容忍短暂清辅音；不在播报结束 80–320ms 后重建麦克风 |
| 按过零率把整段归为歌声；把“嗯/哦”等简短回应当噪音 | 真人语音被丢弃 | 移除无依据的歌声判定与文字填充词黑名单；保留声学能量、噪音比、周期性和连续窗口检查 |
| 网络握手、等待最终转写期间没有读取 AudioRecord；批式下一轮清空旧队列 | 采集缓冲溢出、丢句 | 独立 PCM 采集线程，有限缓冲；保留最多三段待识别录音，溢出明确提示；会话重建隔离旧回调 |
| Socket 已结束仍继续上传，失败被返回空串 | 空等十几秒，网络/鉴权错误被误认为用户没说话 | 结束信号及时退出；检查发送结果、连接/最终结果超时；错误提示与受限重试，健康检查重启死亡线程 |
| 讯飞纠错后选择更长的旧 append 文本 | 纠错结果丢失，旧词句复活 | 按 sn 与 rpl/rg 替换整段，以纠错后的序列为准，支持空替换和连续纠错 |
| 回声过滤永久剪去与 AI 相同的词句 | 用户引用、纠正 AI 时内容被改写 | 不再剪词；批式已屏蔽播报帧的录音保留原文；实时仅在播报窗口匹配近似逐字回声 |
| 云端语音依次等待多个服务商，回调没有代次检查 | 回复无声等待数十秒；打断后旧回复突然播放 | 5 秒后转系统 TTS；旧合成结果、播放完成回调及延迟重试不得复活旧回复；初始化重试与播放器准备均有限时 |
| AI 回复固定走媒体音量，闹钟使用闹钟音量 | 媒体音量为零时，闹钟有声但回复无声 | 回复沿用闹钟/耳机输出规则；正常采集启用设备支持的 AEC/NS；对话时压低音乐而非停止前台服务 |
| 后台启动 microphone FGS 被 Android 拒绝后未重试 | 后续后台识别可能被系统静音 | 可见 Activity 恢复时，在已有录音权限下重新申请 microphone 前台服务类型 |
| “不要关闭闹钟”包含“关闭闹钟”；中文数字按后缀匹配 | 正常对话误关闹钟；45 分钟变成15分钟 | 停止指令采用明确句式，贪睡拒绝否定/解释句；完整解析中文数值，拒绝超范围时长 |
| 首次解锁前读取凭据保护存储；修改时区仍沿用旧绝对时间 | 重启后漏排、时区变更后错时 | 解锁前仅用设备保护存储，迁移后以其为准；时间/时区变化重算本地排期 |
| 排期全部失败仍回报成功；保存中切换模式或反复测试 | 假保存、混用早晚设置 | 只有实际登记成功才记录成功；保存期间锁定编辑、测试；同步失败明确计数，保留旧闹钟 ID |

## 已执行验证

- `KOTLINC=... bash tool/voice_alarm_regression.sh`：15 个离线行为回归场景。
- Kotlin 2.2.0 编译语音闹钟 Activity、Service、Scheduler、Receiver 及其辅助类，使用 Android API 35、AndroidX Core 1.13.1、OkHttp 4.12.0、Okio 3.6.0 的真实类库；不包含未修改的 Flutter MethodChannel 桥接类。
- Flutter 3.35.3 定向分析 `lib/voice_alarm/voice_alarm_page.dart`；现有未使用字段和弃用 API 警告仍在。
- `flutter test --no-pub test/quote_scheduler_resilience_test.dart`：4 个既有排期回归测试。

这些结果验证实现和回归场景，不是完整 APK 构建、真机录音或识别准确率报告。新增 CI 执行离线回归；仓库现有 Android 构建工作流继续负责 APK 验证。

## 98% 成功率的实测口径

目前没有真实设备录音、已配置语音服务账户及标注语料，因此不能声称达到 98%。AEC/NS 的实际效果依赖设备；单麦克风 VAD 不具备声纹身份认证，不能保证在多人同时说话或信噪比极低时只识别目标用户。

每个真实对话轮次单独记录：场景、设备/Android 版本、耳机、服务商、模式、原句、识别结果、AI 回复、实际是否有声、是否需要重说、失败原因、用户说完至首个回复音频的耗时。漏录、错识别改变含义、误执行闹钟指令、重复/过期回复、无声和必须重说均计为失败，不能只统计服务返回 HTTP 200 的请求。

普通条件建议至少 1000 轮，分布到安静房间、风扇/空调、背景音乐、轻声短句、正常长句、播报后立即接话与连续多轮；不同设备和三家 STT 分开报告。汇总与各普通场景均检查成功率是否 ≥98%，同时报告样本量和置信区间。单次重试成功另计“恢复成功”，不覆盖首次失败。

速度分别记录端点等待、STT、AI、TTS 和端到端 P50/P95。代码中 `stt.complete`、`ai.ask.complete` 及已有播放起止事件可辅助定位延迟；主观“快了”不能替代测量。新建配置默认批式静音等待由5秒改为1.2秒，实时由2.4秒改为1.4秒，最终转写后合并等待降至300ms；已有用户保存的静音时长保留，可在高级设置调整。

异常场景需逐项验证：撤销麦克风权限、系统麦克风关闭、其他应用占用、断网、401/403、限流、连接中途关闭、STT 空结果、TTS 合成失败/超时、播放回调缺失、切换早晚闹钟、播报中停止/贪睡、耳机断连、重启且尚未首次解锁、切换时区。验收要求是原因可见、不会永久卡住、有“重新聆听”“重试上一次录音”或“输入文字”恢复路径。

长句录音最长时间、排队上限与5秒语音合成兜底均有边界；背景人声不能靠纯音量或过零率可靠区分，强干扰场景需要实际采样后决定是否引入经过评估的神经 VAD/声源分离模型。
